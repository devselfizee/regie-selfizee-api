1 Principe de la synchronisation

Chaque borne envoie directement à la plateforme de suivi son journal de ventes et son état. Rien ne transite par Pikcloud ni Booth : une panne de la synchronisation photo n'a donc aucun effet sur le chiffre d'affaires, les commissions ou les alertes.

Ce que la borne envoie

Le journal des ventes (montant, moyen de paiement, formule, statut) et son état (en ligne, papier, ruban, erreurs).

Ce que la borne n'envoie jamais

Ni photo, ni donnée personnelle, ni donnée de carte bancaire (numéro, expiration, nom du porteur).

2 Authentification de la borne

Chaque borne possède sa propre clé API, à envoyer dans chaque requête :

Authorization: Bearer rgs_k3f9a2mx_8Hq2vW…(43 caractères)
Le borne_id doit correspondre à la clé Le champ borne_id du JSON (ex. MT-0042) doit être exactement l'identifiant de la borne à qui appartient la clé. Sinon la requête est refusée (403 BORNE_DIFFERENTE).

3 Envoi des ventes

POST /ingest/v1/transactions — un lot de 1 à 500 ventes, envoyé après chaque vente ou par petits lots.

// Lot de ventes
{
  "schema_version": "1.0",
  "borne_id": "MT-0042",
  "envoye_le": "2026-10-05T23:15:02+02:00",     // avec fuseau
  "logiciel_version": "3.4.1",
  "rattrapage": false,
  "transactions": [
    {
      "transaction_id": "ING-20261005-000184",   // clé anti-doublon
      "horodatage": "2026-10-05T22:47:31+02:00",
      "montant_ttc_centimes": 800,              // 8,00 € en centimes
      "devise": "EUR",
      "statut": "accepte",
      "module": { "type": "INGENICO_SELF_2000", "numero_serie": "SELF2K-19A77310" },
      "moyen_paiement": "sans_contact",
      "reference_monetique": "AUT-554821",
      "produit": { "code": "BANDE_4", "libelle": "Bande 4 photos", "nb_tirages": 2 }
    }
  ]
}

Enveloppe du lot

ChampDescription
schema_version *Toujours "1.0".
borne_id *Identifiant de la borne : majuscules, chiffres, - et _ (3 à 64 caractères).
envoye_le *Date et heure de l'envoi, avec fuseau.
logiciel_version *Version du logiciel de la borne.
rattrapagetrue quand la borne renvoie un historique après une coupure.
transactions *Liste de 1 à 500 ventes.

Une vente

ChampDescription
transaction_id *Identifiant donné par le module de paiement, unique pour la borne. C'est la clé anti-doublon.
horodatage *Date et heure de la vente, avec fuseau.
montant_ttc_centimes *Montant TTC en centimes, nombre entier (800 = 8,00 €). Toujours positif, y compris pour un remboursement.
taux_tva_pctTaux de TVA (ex. 20). Par défaut : 20 %.
devise *"EUR" (seule devise gérée).
statut *accepte, refuse, annule ou rembourse. Envoyer aussi les refus : ils servent au taux de refus et aux alertes.

module.type *INGENICO_SELF_2000, MONNAYEUR, STRIPE_TERMINAL… Un code inconnu est rejeté : demander à Selfizee de l'ajouter.
module.numero_serieNuméro de série du module de paiement.
moyen_paiement *cb (carte insérée), sans_contact, especes, mobile (Apple Pay / Google Pay), autre.
reference_monetiqueRéférence du prestataire (n° d'autorisation…), pour le rapprochement avec les relevés Ingenico. Interdite pour les espèces.
produit.code *Code de la formule vendue (ex. BANDE_4).
produit.libelleLibellé lisible de la formule.
produit.nb_tirages *Nombre de tirages imprimés (0 à 100 ; 0 pour un refus).

* obligatoire. Tout champ non prévu par le schéma est refusé.

Aucune donnée de carte bancaire Numéro de carte, date d'expiration, nom du porteur : interdits. Le schéma refuse tout champ inconnu, ce qui empêche une fuite par erreur.
Horodatages avec fuseau, horloge à l'heure 2026-10-05T22:47:31+02:00 ou …Z. Sans fuseau : rejeté. Horloge synchronisée par NTP : la date de la vente détermine le lieu auquel elle est attribuée.

4 Réponse de l'API

Un lot traité renvoie 200 OK, même si certaines ventes sont rejetées. Les ventes rejetées sont gardées par la plateforme dans sa file d'erreurs, avec leur motif : la borne n'a pas à les renvoyer.

{
  "import_id": "1824",
  "recues": 4, "creees": 3, "doublons": 0, "rejetees": 1, "non_affectees": 0,
  "erreurs": [
    { "index": 2, "transaction_id": "MON-000912", "code": "MODULE_INCONNU",
      "message": "Type de module \"MONNAYEUR_X\" absent du référentiel" }
  ]
}
ChampSignification
creeesVentes nouvelles enregistrées.
doublonsVentes déjà reçues à l'identique : ignorées, sans effet.
rejetees / erreursVentes refusées, avec leur position dans le lot (index, à partir de 0) et le motif.
non_affecteesVentes reçues alors que la borne n'est affectée à aucun lieu à cette date : gardées et signalées à Selfizee. Rien à faire côté borne.
Code d'erreur (par vente)Cause
SCHEMA_INVALIDEChamp manquant, mauvais format, champ non prévu (le message précise lequel).
MODULE_INCONNUmodule.type absent du référentiel de la plateforme.
DEVISE_NON_GEREEDevise autre que EUR.
CONFLIT_DOUBLONCe transaction_id a déjà été reçu (ou figure deux fois dans le lot) avec un contenu différent. La vente d'origine n'est jamais écrasée.
HORODATAGE_FUTURVente datée de plus d'une heure dans le futur : horloge de la borne à resynchroniser (NTP).

5 Remboursements

Un remboursement est une nouvelle vente, avec son propre identifiant, qui pointe vers la vente d'origine. La vente d'origine ne doit jamais être renvoyée avec un statut modifié : elle serait rejetée (CONFLIT_DOUBLON).

6 Signal de vie (heartbeat)

POST /ingest/v1/heartbeats — toutes les 5 minutes, même sans vente. C'est ce qui permet de distinguer « pas de client » de « borne en panne ».

{
  "schema_version": "1.0",
  "borne_id": "MT-0042",
  "heartbeats": [
    {
      "horodatage": "2026-10-05T23:15:00+02:00",
      "logiciel_version": "3.4.1",
      "papier_restant": 310,  "ruban_restant": 316,
      "imprimante_ok": false, "module_paiement_ok": true,
      "erreurs": [ { "code": "PRN_JAM", "message": "Bourrage papier", "composant": "imprimante" } ]
    }
  ]
}
ChampDescription
horodatage *Moment de la mesure, avec fuseau.
logiciel_version *Version du logiciel.
papier_restant, ruban_restantNombre de tirages restants (alertes consommables).
imprimante_ok, module_paiement_okÉtat des périphériques.
erreursErreurs en cours : code, message, composant (imprimante, module_paiement, camera, ecran, reseau, logiciel, autre).

Jusqu'à 2 000 heartbeats par lot (rattrapage). Réponse : 200 OK avec { "recus": 2, "crees": 2, "doublons": 0 }. Un heartbeat déjà reçu (même borne, même horodatage) est ignoré.

7 Fiabilité : file d'attente et rattrapage

Objectif : aucune vente perdue La plateforme calcule ce qui est reversé à chaque lieu. Une vente perdue, c'est une commission fausse.

Rattrapage après une coupure

  1. File d'attente persistante. Chaque vente est écrite sur le disque de la borne (SQLite, fichier…) avant toute tentative d'envoi. Elle survit à un redémarrage ou à une coupure de courant.
  2. Retrait seulement après un 200. Tant que la plateforme n'a pas répondu 200, la vente reste en file.
  3. Renvois sans risque. Même borne_id + même transaction_id + même contenu = doublon ignoré.
  4. Attente croissante entre les essais (30 s, 1 min, 2 min, 5 min, puis toutes les 15 min), avec un peu d'aléatoire pour que toutes les bornes ne réessaient pas en même temps.
  5. transaction_id stable. Le même identifiant désigne toujours la même vente, avec les mêmes valeurs. Ne jamais le réutiliser pour une autre vente.

Exemples avec curl

# Ventes
curl -X POST https://<url-api>/ingest/v1/transactions \
  -H "Authorization: Bearer <clé de la borne>" \
  -H "Content-Type: application/json" \
  --data @transactions.json

# Heartbeat
curl -X POST https://<url-api>/ingest/v1/heartbeats \
  -H "Authorization: Bearer <clé de la borne>" \
  -H "Content-Type: application/json" \
  --data @heartbeat.json

9 Mise en service d'une borne

  1. Création sur la plateforme (Selfizee) : identifiant, gamme, module de paiement. La clé API s'affiche une seule fois.
  2. Installation de l'identifiant et de la clé dans la configuration de la borne.
  3. Affectation au lieu (Selfizee), avec la date de début. Les ventes sont rattachées au lieu actif à leur date.
  4. Vérification : la borne passe « En ligne » dans les 5 minutes (heartbeat), puis une vente test apparaît dans les statistiques du lieu.
